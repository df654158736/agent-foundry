# v0.1.0 验证记录

本版定位为开发者预览。源码携带可复演的验证入口，模型配置由使用方提供。

| 检查 | 方法与判据 |
| --- | --- |
| 环境与发行物 | 在独立目录解压源码 ZIP，用 uv 0.12.2、CPython 3.12.13 和 uv.lock 在全新虚拟环境安装，核对 ZIP 的 SHA-256 |
| 单业务隔离 | 初始化空项目与班次示例，确认新项目只读自己的工具和系统提示词。库存场景通过 OpenAI 客户端的受控 HTTP transport 发起两次协议调用，核验工具参数、回执和最终正文 |
| Skill 与多轮 | 运行班次 fixture，检查模型输入的实际工具 schema、业务 Skill 文件读取回执、第二轮日期修改及站点保持 |
| 纠错与相邻保护 | 故障基线按站点查班次，遗漏日期；候选同时核对站点和日期。shift 由 FAIL 到 PASS，missing 维持 PASS。原问、脚本模型与独立判据保持相同 |
| 证据完整性 | 各 attempt 独立保留。使用 AgentGauge 0.4.0.dev10 的 Trace.model_validate_json 对示例的交换文件做格式校验 |
| 升级 | 同版本并行迁移演练保留业务资产、权限边界和原项目，框架文件被定制时阻止静默覆盖。下一版发布时仍须真正进行跨版本测试 |

复演：在发行目录执行 README 中的 unittest 和 scripts.prove_iteration。受控模型负责驱动场景，不产生可用于声称真实模型自主性的证据。真实提供商的稳定性、复杂授权写操作、跨进程业务恢复、全新 Codex 宿主的 reviewer 自动发现和独立开发者的接入耗时仍须分别验收。

## v0.1.1 开发资产与故障复验

- 在 v0.1.0 业务项目上执行并行升级，核对 business 和 evals 目录的内容摘要不变。新版安装了五份个人方法 Skill 及配套材料，原三个 Foundry Skill 继续作为任务入口。两个 reviewer 的职责和详细判据来自原配置，保留项目只读限制。
- Codex CLI 的 skills/list 在初始化后的示例目录返回八份启用的 repo 级 Skill，来源路径均在该项目内。ZIP 与新建项目逐文件比对了 Skill 及两个角色。当前开发宿主调用了 spec_delivery_reviewer；独立新宿主能否实际调起该角色，仍须结合宿主支持的模型和角色配置验证。
- 冻结同一原题、脚本模型与 Oracle 后，独立复核者从 shift 第 2 轮轨迹定位到首次错误。输入为东站 5 月 12 日，工具回执给出 5 月 11 日；候选回执和用户答复均恢复为 5 月 12 日 14:00–16:00。missing 两轮都正确披露班次未发布。脚本现在还逐项核验注入故障恰好造成预期的两项失败。
- 本次场景以受控模型和预置候选检验观察、归因与复核。真实模型自行发现和修复未知问题的成功率需要独立样本。

## v0.1.3 跨业务的复核和续接

从新建的自提班次包出发，在受控基线的一条来源记录中附加未经执行的预约确认。基线和干净候选各两题，冻结自动分均为 2/2。无对话历史的 spec_delivery_reviewer 从包内 AGENTS.md 和 CHECKLIST.md 定位两批材料，追到原查询回执首先包含错误承诺，判基线业务 2/2、正文 1/2，候选两轴均 2/2。主会话登记实际复核意见，正向 compare --require-review 退出 0，将有错误承诺的批次作为候选时退出 1。此对照验证受控发现的交接、复核与关闭；跨宿主自动拉起和真实模型在陌生业务上的自主修复率仍待测。

用打包的 v0.1.2 初始化项目，再从 v0.1.3 ZIP 并行升级。原业务 Spec 保留，新项目从正常 CLI 执行 eval 和 review，两题初始均为待复核。原始运行未登记结构化意见时也显示待复核。

## v0.1.4 空业务包开工路径

在空白备件项目中，直接使用随包开发指引里的工具和 Skill。受控模型通过正常 chat 入口先读取 Skill，再调用库存工具；实际模型请求中核验了 Skill 目录项、读取到的正文、工具 schema 与库存回执，交付为 P-7 可领用 12 件。缺失 YAML 文件头的同名文件被运行时跳过，doctor 会报告其路径。此验收验证了装配与接线，模型自主判断须以具体业务获准的真实请求验收。
