# 目标对齐

用用户实际会拿到的结果判断方案是否合适。截图里的症状、当前代码最容易改的地方、历史方案的设计目标，都只是调查线索。

## 第一准则（智能体设计与排障，强制）

**第一准则（强制）：信息供给优先，正确归因并保障完整交互。** 适用于智能体及 Harness 的设计、开发、排障、修复和评审。在遵守上位契约与项目宪法红线的前提下，下列准则优先于下文的实现选型、模块设计原则和评测指标；必须逐项对照，不是可选优化建议。

1. **让模型拥有正确判断的依据。** 在模型理解目标、选择能力、填写参数、解释回执和决定下一步之前，尽可能提供当前任务所需、权限内可用、准确且可理解的信息与自主查证能力。不能只看后台有没有信息，必须核对模型在每个实际决策时点（特别是首次相关调用前）真正看到了什么、还缺什么、能否自行取得。工具说明、参数约束、业务事实、已确认条件及工具回执中的来源、匹配关系、适用范围和不确定性等有决策意义的信息应如实提供；区分候选、已核实事实与业务等价性或执行授权，不能把候选呈现为已确定事实。已知信息及时提供，缺项提供可发现、可凭已有线索使用的查证路径，避免让模型猜参数才能获取填参依据；不能把决策前已经需要且可用的信息拖到失败之后才提供，也不能仅凭后台存在信息或一次碰巧正确就认定供给充分。模型出错时先排查信息供给，并提供具体纠错反馈，允许在同一任务内自主修正；不得以新增校验或固定步骤代替应有的信息供给。
2. **正确归因与修复，坚守宪法红线，保障正常人机交互。** 单个 Bug、金标或通过率只是诊断线索，不是生产修改目标。必须依据真实链路的模型可见输入、模型决策、工具回执、实际执行范围和交付结果区分信息供给缺口、Harness 确定性契约缺陷、模型能力或语义判断问题、基础依赖问题及评测断言问题，并在责任层修复。模型已有充分、准确、可理解的依据仍出错，不等于 Harness 有缺陷；不能为了个别样例将模型应自主完成的判断固化为程序逻辑，例如新增原话放行门、固定工具顺序、强制查证或普遍兜底硬规则。确定性硬约束须有权限、明确用户条件、口径、类型、事实、状态或交付不变量等真实客观契约依据。 独立模型、路由、审查或历史理解的推断只能作为判断依据；不能因它来自第二个模型就把推断升格为用户确认或客观放行约束。基础依赖异常、能力不可用或暂时无法解决的问题可以阻塞业务结果，但不能因此让人机交互失败：智能体必须用用户能理解的自然语言完成交互，先交付已核实且可交付的结果，讲清实际问题、影响范围、未完成事项，有可行下一步就告知用户；原因未查明时如实说明已确认到哪一步，不编造结果，不以错误码、通用报错或重试按钮代替正常交流。**业务结果是否成功与人机交互是否合格必须独立判断。** 业务受阻但交互满足上述契约时，交互可判通过，业务结果仍记为阻塞；不得为使金标变绿而收紧模型自主性，也不得以降低验收标准遮盖实际失败。
3. **模型自主表达，服务端守护可信事实（强制）。** 智能体的最终正文应由模型依据用户目标、服务端可信且实际可见的事实和执行/失败回执自行理解、组织自然语言；服务端负责权限、真实数据、计算、证据引用及可确定的交付事实验证。不得为防止模型编造数值或为固定话术验收，把正常回答限制为单一占位符、固定正文模板或服务端代写，也不得将解释问题、披露范围、交互和给出下一步的责任转交给模板。可使用可选的细粒度可信事实引用，由服务端核验并渲染数值，不替模型决定表达结构；需纠错时给出实际缺项及可选依据，让模型同任务修正。只有真实模型不可用等降级情形才采用明确标识的最低限度事实交付，不得成为正常路径。评审核对正常入口实际生成的用户可见正文及其作者、模型看到的证据、实际使用的事实引用和失败反馈；保持事实准确和表达自主两项独立验收。 模型可见的可信事实与完成验证应复用同一事实投影，不得先披露合法事实又因验收侧缺项阻止正确表达；终态若承诺可续接或可查看历史，其必要可信状态应在终态可见前就绪，不能依赖客户端继续消费已结束的流。

具体设计时，及时提供并复用仍在有效范围内的可信信息；由拥有执行责任的运行时绑定可信执行参数。评估有代表性的参数类型，比较因信息缺口引起的猜填、拒绝和重试。修复共享契约时验证合法相邻场景；保留未证实归因和实际阻塞，涉及上位设计调整时与开发者对齐。

## 已确认设计决策必须贯穿交付

- 把用户原始目标及已经明确确认的每个设计决定（包括明确排除的做法）作为可观察行为纳入 Spec，逐项对应正常入口、责任方法或接口、实际执行判据与验收场景。实施前独立核对整个 Spec 及继承契约是否符合共识，不能只检查 Spec 内部自洽。
- 决定移除某道放行条件时，沿正常首次执行、纠错、恢复和最终交付逐处检查，不能通过改名、重新举证、新前置条件或兜底恢复等效阻断。明确原先被误拦而现在应放行的正例和必要反例。
- 保留原始输入、预期用户结果和已确认验收范围。诊断样例、改写输入、局部成功、过程单测只是支持证据，不能替代失败的原始要求。部分成功及实际阻塞如实记录；改变目标或验收标准须与用户对齐。独立评审先检查共识与 Spec，再检查实施及证据与二者的一致性。实现全绿但 Spec 偏离目标，仍属于交付失败。

## 开放自然语言覆盖与确定性约束

- **具体方法逻辑能否覆盖全部受支持的自然语言提问，是重要的开发设计标准。** 对解释用户原话或可以阻断执行的每个方法，先判断可覆盖的合法表达、它要防止的具体错误和可信判据。覆盖不足时，评估误拦的合法请求、用户代价和存在意义，再决定保留、仅作为辅助证据、收窄还是替换。单一问法或少量金标成功不能证明开放输入覆盖；必须用不同表达和组合取证。
- 在模型面对每个接口前应用第一准则。让模型根据可用业务事实和授权工具理解自然语言、解决不确定性；服务端只对权限、字段类型、真实数据与执行口径、用户已确认约束等客观契约作确定性核验。普通语义选择合法且无已知实质冲突时，字面未命中、缺少预定义别名或无法穷尽候选都不构成拒绝提案的理由。更严格的放行条件必须能证明独立真实契约，例如用户明确要求精确匹配、身份、权限或实际改变执行范围时的业务等价性。
- 提案违反真实契约时，回执返回具体冲突或缺失依据，保留已经确认的目标和条件，让模型在同一任务内自主补查、修正或继续。只有仍存在无法自行消除、会改变结果的实际歧义，或用户明确要求选择时才请用户确认。
- 从正常入口用未预设的合法等义问法、首次提案错误后可自主纠正的用例，以及真实冲突或歧义的反例取证，核对实际执行范围是否保留用户意图。不能用少数样例成功或规定工具顺序替代开放自然语言验收。

## 开放式智能体的设计原则

- 以用户目标、授权和已确认的业务契约裁决设计与验收。金标是验证这些要求的样本。模型可以采用不同的合法路径。实际轨迹保留原条件、遵守权限、用可核实的事实和证据交付，且用户能自然理解和继续，就按实际表现验收。
- 生产中的硬约束必须保护独立于金标样例的真实要求。验收断言若强制了契约未要求的工具顺序、澄清方式、轮次或答复措辞，应修正验收。发现真实缺陷时，在首次违反通用契约的层修复。
- **交付红线。** 任务受阻时，保留用户条件，先交付权限范围内已核实且可交付的结果。即使没有可交付的结果，也用用户听得懂的话说明哪些事项未完成、为什么停下，有可行的下一步就一并给出。原因尚未查明时，如实说明能确认的状态。用户只看到错误码、通用报错或重试按钮，交互验收不通过。尚未取得的业务结果单独记为阻塞。

## 把目标落实到可观察行为

- 从用户原话、原始场景和前后轮确认目标。指出用户希望在什么入口、看到或做到什么，以及当前哪里没达到。用一句可以被验证的话表达目标。
- 确认当前链路实际发生了什么。能读取原输入、输出、运行轨迹或实现时，用这些证据区分表面症状和造成偏差的决策。只看到部分证据时，把推断和已核实的事实分开。
- 区分用户指定的硬约束、已承诺的契约与可以重新权衡的历史选择。历史取舍如果和这次目标冲突，明确冲突、改动成本和影响。遵守权限边界，涉及既有契约变更时把它作为显式设计决定。

## 用反例选方案

- 先问一个反事实：如果采用最直接的修法，原症状消失后，用户还可能因为什么说「这不是我要的」？把这个反例变成验收场景。
- 对有实质取舍的问题，比较直接修法和能覆盖真实目标的方案。按用户在意的结果、证据质量、复杂度和运行成本做选择。先淘汰达不到目标的方案，再在其余方案里选足够简单的。
- 用原场景和一个真正改变决策的变体验证方案。只改措辞的变体通常不够。可以改提问重点、输入类别、结果方向或证据完整性。复杂任务按风险补充反例。
- 对开放式问答，分别判断理解用户意图、组织表达、核验事实和兜底由谁负责。根据第一准则和事实风险明确分工：模型自主理解、决策和组织正常正文，服务端守护可信事实及客观契约。不得以固定程序代替开放语义理解或正常表达。
- 对新增、保留或放宽的 Harness 约束，说明它保护的结果、可信判据、模型能否自行纠正，以及它带来的等待、轮次、工具调用、误拦和风险。针对实际模型，用同输入、同配置和同依赖的轨迹对照，核对合法请求是否更顺、错误结果是否仍能挡住。

## 问数智能体的职责与红线

- 把可迁移的问数经验写入问数智能体实际加载且职责匹配的运行时 Skill，写明适用条件、优先核验的证据和证据不足时的做法。用不同指标、对象或问法验证经验能否迁移。具体题号、业务值、固定问句和故障轨迹留在金标或回归证据。
- 模型负责理解用户目标、选择指标与分析路径、提交参数。收到校验反馈后，由模型决定补证据、修正提案或向用户澄清。涉及用户明确目标的实质变更时，先取得用户确认。
- 服务端负责权限、口径、范围、事实、执行和验收。用户明确的指标、范围、筛选、期间、粒度和比较基准须贯穿提案、冻结和执行。普通语义映射遵循开放自然语言覆盖与确定性约束原则；服务端替换执行来源或实质改变已确认范围时须有权威证据证明等义或取得用户确认。按单例写死业务决策或静默改变显式约束均属于越界。
- 把模型能据此采取行动的反馈纳入校验设计。校验失败时，服务端指出哪个字段或哪项约束未通过、具体原因和可用的核验证据，提供当前权限下的已核验候选（如有），并保留用户原始约束和其他已核验条件。验收比较模型提案、模型实际收到的反馈、冻结计划和实际执行，验证模型能据此补证据、纠正传参或向用户澄清。
- Lite 等轻量入口要核对运行时实际加载的说明、Skill 和上下文。常驻内容保留完成任务所需的职责、边界和定位入口；能力细节与语义资料按需获取，服务端继续使用完整权威数据校验。对固定必读或全量灌注，用实测判断它是否改进决策与交付，以及交互和资源成本。

## 对话可用性验收

- 对话产品分别验收业务结果与对话可用性。要求交付业务结果的场景，两项都达标才算完整通过。预期拒答或停止的场景按相应契约验收。缺少必要证据的结论标为未验证。
- 从真实入口逐轮看原问题、用户看到的消息或卡片、用户的选择或补充、后续动作及最终交付。核对是否只问会改变结果且无法从可信上下文确定的问题，是否重复询问已知条件，用户能否凭清楚的理由和选项作答，答完能否带着原条件在同一任务继续。核对回答能否让用户理解结果、关键口径以及证据或可执行下一步。缺少前端展示证据时，按已观察到的内容评判并注明边界。
- 金标写明各场景要达成的用户行为、何时应澄清及何种体验算失败。次数、重复询问、续跑、范围和证据可用结构化断言，问题好不好答、选项是否能区分、回答是否容易理解，要结合实际文案和上下文判定。允许合理澄清和等价交互路径。

## 开工和验收

- 跨层故障先判责任和验收目标，再选改法。沿真链写明首次偏离已确认契约的输入、预期、回执和责任层。对 Harness 修复，问「上游缺项保持现状，Harness 保留用户条件、准确说明缺项和处理途径，并停止受阻操作，本轮是否就算通过？」若是，只修已证实的本层缺陷，业务结果仍记为阻塞。已核实上游提供合法证据而本层漏接时，修本层的通用契约。归属未证实时继续定向取证。
- 已证实问题来自模型能力且 Harness 符合契约时，按模型问题记录。模型能力随版本变化，禁止为了兼容单例错误提案而新增替代模型语义的补丁或放宽有效客观执行约束；如果已有门本身缺乏真实契约依据，应依据第一准则在责任层处理。保留用户条件和可交付结果，用用户能理解的话说明实际阻塞、未完成项和可行的下一步。Harness 和交互验收与业务结果分别判定。
- 涉及产品行为或架构取舍时，在动手前向用户简短说明理解的目标、推荐方案及关键取舍，并给出能区分方案的验收场景。已有授权且判断依据充分就继续。只有答案会实质改变方案、又无法从现有证据判断时，才请用户确认该分歧。
- 实现时沿真实入口核对用户拿到的结果。证据准确、接口通过或文案变短，都不能替代目标验收。检查关键变体和用户要求保留的行为。受环境限制时说明验证到哪一层。
- 新证据改变责任归属、前置是否成立或验收目标时，先说明改变了什么、本轮做到哪里，再按新的判断推进授权范围内的工作。不能为了让已有方案过关，悄悄缩窄目标或降低验收标准。用户只要诊断或方案时，交付到该阶段。

## 判断示例

归因回复太长，直接修法是缩短模板。如果用户要的是能回答开放式业务追问，用「成本下降，为什么毛利只涨了一点」来检验。仅列最大贡献项可能漏掉抵消因素。更匹配的方案是让模型结合原问题和本轮核验过的事实组织正文，由代码校验事实引用并在失败时兜底。额外模型调用的耗时，以及证据不足时能答到哪一步，都进入取舍和验收。
