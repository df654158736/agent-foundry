# 智能体七维评测与诊断

用于问数、检索、分析、报告生成、工具执行和多轮工作流等智能体。输入可以是当前会话、指定历史会话、导出的评测报告、实际运行轨迹或授权执行的金标。输出既要有可比较的评分，也要让后续开发者凭证据定位问题、验证优化效果。

若同时提供源码，允许开展源码级归因并注明所核对的版本；仅有已发布服务时，开展运行时诊断，记录具体可见事件、裁决、工具及配置，不猜测内部实现。纯评分任务以读证据、评价和报告为主；执行新测试、修改实现、修改金标或部署须在用户授权范围内。

## 1. 评测原则

遵循目标智能体已确认的产品契约与设计红线。按本发行版的 [goal-aligned-design](../goal-aligned-design/SKILL.md) 应用智能体第一准则；具备真链取证能力时，按 [debug-agent-reallink](../debug-agent-reallink/SKILL.md) 选择与风险相称的取证方式。不依赖这两个 Skill 的具体安装路径，以下原则可独立使用：

- 信息供给优先。核对每次关键决策发生前，模型实际看到的用户条件、可信事实、工具定义、参数语义、回执、上下文，以及自主取得缺失信息的路径。区分候选、已验证事实、业务等价性和执行授权。
- 模型自主理解、选择、查证、纠错和组织自然语言；Harness 负责权限、类型、已确认约束、真实数据、计算、来源、状态、恢复、预算及客观交付核验。正常回答遵循可信事实，不因防止编造而让固定模板代替模型表达。合法的不同执行顺序、证据复用和主动补查均可接受。
- 首次偏差、实际后果、根因和修复责任分别记录。模型错误不自动证明 Harness 缺陷；工具或依赖失败也不自动证明调用方有错。不要为通过个别金标提出硬编码问法、固定工具顺序、强制查证、强制澄清或原话匹配门。确定性门控需要真实客观契约。
- 业务验收、Harness 正确性、人机交互独立判断。业务阻塞时仍评估能否保留条件、如实解释原因并交付已经验证的部分；正确说明阻塞不等于业务结果通过。正常无数据、零值、不支持、无权限及依赖错误按真实语义区分。
- 金标和评分断言也要接受契约审查。发现冲突时保留冻结判分与独立评测结论，标记待确认，给出证据及修订方向。不能用预期值倒推生产规则，也不能为了通过率放宽断言。

## 2. 按运行证据评价

先声明评测范围（对象、用例、真实入口、环境、项目或权限、可得的模型/Agent/Skill/提示词/工具/实现版本、测试时间和证据等级）。核对原问、多轮已确认条件、预期业务语义、合法执行路径与可获得的独立事实或 Oracle。用例不适用、前置未就绪或缺少金标时，仍可评价已有证据支持的维度。

1. 将用户问题、会话轮次、模型调用、工具与服务回执、Harness 裁决、中间产物、实际结果和用户可见答复按发生顺序关联。注明任务、会话、trace、事件序号等可用定位信息。
2. 对影响结果的决策核对当时的模型可见输入和可用查证途径、实际选择、工具入参和回执、下一步消费事实及状态。只读取实际可访问的已授权证据；配置清单、摘要或版本摘要不能代替实际模型输入。可见内容截断、未埋点、脱敏导致不可判定时，明确缺口。
3. 找出每项问题第一次**可观测**的偏差：预期契约、决策环节、实际行为、证据和影响。继续检查后续纠错、重试、恢复、部分交付和最终对用户的解释。通过用例同样检查空转、不必要的澄清、重复检索、违规路径和被掩盖的设计问题。
4. 根据七维判据评分，单独列出具体工具、Skill、提示词或 Harness 裁决的可归因问题。根据实际证据区分已确认事实、合理怀疑、无法确认；源码不可见时给出需要开发者核实的接口、行为或裁决名称。
5. 给出通用改进建议、可能负责层及验证方式，至少说明需要保护的共享契约和有代表性的变体/反例/相邻场景。无缺陷或证据不足时如实记录，无需强造优化任务。

评估历史会话时使用已有会话及证据，缺少必要材料才请求补充；仅有聊天截图或答复时，评价可观察的业务和交互表现，不从答复反推隐藏的模型输入、工具或代码。如果用户要求真链评分，按实际授权复跑并保留所有结果，不筛掉失败尝试。不要把测试用例的预期值作为模型答题时已经知道的信息。

## 3. 七个评分维度

每维给出 1–5 分（有足够证据时）或“未评分”，同时列出已检查范围、结论、理由、证据引用、严重问题及改进方向。没有相关调用、缺少必要证据或契约待确认时说明原因，不给猜测分。下面的观察项按任务相关性选择，没有要求每个用例必经这些步骤。

| 维度 | 评价对象与判据 |
| --- | --- |
| 业务结果 business_result | 原始目标和已确认约束是否保留；实际口径、范围、结果和副作用是否正确、完整、有证据；数值或事实使用独立 Oracle、权威资料或已确认业务验收标准；正确区分空结果与错误。 |
| 信息供给 information_supply | 关键决策前是否真正提供准确、充分、可用且可理解的信息；用户约束、目录、权限、上下文、候选及其来源/关系/限制是否清楚；缺项能否通过现有合法工具自主查证；错误反馈是否提供可行动的纠错信息。 |
| 工具设计 tool_design | 实际暴露的工具能力说明、选择条件、schema、参数含义、合法范围、返回结构、来源、错误语义和回执是否与真实接口一致，能否帮助模型正确调用和恢复；区分调用方填参错误、工具契约违约、依赖故障和业务前置缺口。 |
| Skill 质量 skill_quality | 实际加载、使用的技能说明是否完整、准确、及时、与其他指令一致；是否提供有用的方法和判定依据、明确能力边界；是否存在固定问法、强制步骤、相互冲突或过度限制；模型未遵循合理 Skill 与 Skill 本身设计问题分开。 |
| 提示词质量 prompt_quality | 实际生效的系统、任务和运行时指令是否清楚表达角色、目标、职责、上下文使用、错误处理和交付；冲突、无必要重复、遗漏和固定分支是否影响决策；指令合理但模型未遵循时，记录模型表现与证据。 |
| Harness 合理性 harness_quality | 已观察的路由、权限、类型、已确认条件、客观证据与放行/拒绝契约是否合理；状态与多轮继承、恢复、重试、预算、终止和交付是否一致；错误是否能反馈给模型继续自主纠正；是否代替模型作语义判断或正常正文表达。 |
| 人机交互 human_interaction | 用户是否理解真实结果和实际执行范围；必要时澄清、提供有效选项、继承确认结果；受阻时准确说明原因、影响及未完成项，并交付已核实的事实及可行下一步；正常正文由模型基于可信事实自主表达。 |

信息供给着重判断决策时可用信息，工具、Skill、提示词、Harness 着重判断提供这些信息与进行裁决的设计。一个问题可能影响多个维度，复用同一证据/问题记录，避免把同一运行偏差统计成多个独立缺陷。

### 评分尺度（rubric v1）

| 分数 | 有证据支持的评价等级 |
| --- | --- |
| 5 | 本次已覆盖范围内符合相关契约和设计原则，未发现实质性缺陷。 |
| 4 | 基本合理，存在轻微改进空间，已观测主流程正确。 |
| 3 | 存在明确改进点、可恢复偏差或稳定性风险；尚无证据表明本次产生严重错误，或经合法纠错恢复。 |
| 2 | 存在明显设计/执行缺陷，已经实质影响决策、结果、交互、效率或恢复。 |
| 1 | 存在严重、已证实的核心契约违背或架构红线问题，导致目标严重偏离、事实错误、范围被静默改变等。 |
| 未评分 | 未涉及、不适用、证据不足或验收契约尚未确认；不能按 0 分、满分或失败计算。 |

按缺陷的实际严重性和证据选择等级，不因结果碰巧正确给所有维度高分，也不因业务结果失败给所有维度低分。评分与归因置信度独立；能确认某维缺陷但根因尚未确认时可以给该维低分，责任方保留待核实。评分不替代客观金标验收，也不以平均分覆盖严重违约。默认不计算单一总分；用户明确要求综合分时，公开计算口径、已覆盖维度及缺失项，同时保留每维评分和独立验收结论。

### 对具体资产评分

对运行中实际涉及且有证据的工具、Skill、提示词及 Harness 裁决，使用同一尺度给出名称、可用版本或摘要、证据中的具体调用/加载/裁决、优点、问题、评分与影响。同名资产有不同版本时分开。没有加载/使用的 Skill、未暴露或未调用且无其他直接证据的工具不得推断质量；若实际模型输入中已观测到本该可用的能力未暴露，单独评价供给或接线。不要依据模型数量或调用次数单独判好坏；区分必要调用与可证实的无效空转。

## 4. 诊断报告格式

默认输出中文 Markdown；用户要求其他语言或结构化输出时按要求调整，但保留语义。短会话可简化表达，覆盖全部七维并给出证据等级。

1. **评测结论** — 范围、版本、证据覆盖；业务验收（通过/失败/阻塞/待确认/未评估）、Harness 客观契约和人机交互结论分别列出；原始金标结果与独立复核结论分别保留。性能指标（如实际耗时、Token、工具调用、重试）按可用日志单独统计。
2. **七维评分表** — 每维分值或未评分、已覆盖内容、评分理由、关键证据、改进建议。
3. **关键运行过程与首次偏差** — 按实际时序描述决策前输入/模型提案/实际裁决与执行/结果交付；标记首次偏差、是否恢复及后果；对正常或恢复良好的路径给出正面证据。
4. **具体资产评分** — 逐个列出有代表性的实际工具、Skill、提示词和已观察 Harness 裁决的评价，缺失证据注明。
5. **问题及建议** — 每项发现有稳定编号、预期契约和实际偏差、证据定位、影响、责任分类及置信度、已确认根因或待核实项、建议的通用改进和复验方法。责任分类可包括信息供给、工具或接口、Skill、提示词、Harness、模型语义/能力、基础服务、环境/数据/权限、金标/评分器、规范冲突、待核实；不按错误码直接归因。
6. **证据与未验范围** — 记录可打开的脱敏证据来源、运行标识和未覆盖或待补材料。对真实文件给可定位的路径和事件序号/行号、对远程记录给授权可访问引用。

若用户提供多个运行，先保留各次验收和证据，再按同版本、同契约、同范围汇总评分分布、失败频率、共性问题、首次偏差和已恢复情况。不同版本/契约分组比较，不混算或只选择代表性成功。对比模型或优化前后时同时说明未控制的变量。

导出给开发者或其他评测系统时，可同时提供 Markdown 和 JSON（按需约定文件位置）。JSON 保持 `rubric_version`、`scope`、`versions`、`acceptance`、`dimensions`、`asset_scores`、`findings`、`evidence`、`limitations`、`performance`。七个维度使用上表英文键，评分为整数或 null，未评分原因独立字段。问题关联稳定证据 ID 及运行/轮次/事件，包含实际输入、输出或可定位引用；区分 observed_first_deviation、root_cause、responsible_layer、confidence 和 verification。仅报告脱敏、当前权限内的运行材料，不复制凭据或含敏感内容的完整日志。

## 5. 校准几个常见场景

- 业务答对，但运行时观测到为此添加无客观契约的硬判断或固定正文模板：业务可通过，Harness 和相关交互维度依据明确缺陷评分，注明影响；不能从成功本身推出实现合理。
- 依赖服务确实失败，用户条件保留、模型收到可行动的错误回执，并如实说明已核实和未完成部分：业务记阻塞；Harness 和交互可按独立证据评为 4 或 5；工具及依赖责任依据真实契约判断。
- 模型见到相似文本候选后静默修改明确的文本查询操作数：标出第一次可见的参数变更，核对独立事实、实际模型输入、参数语义、候选关系和回执。若语义说明含混，记录信息供给/工具设计缺口；未能证明源码机制时归因保留怀疑。原词无匹配可以是合法业务结果，旧金标若强制改词应重新审查。
- 仅提供聊天答复，无法得知调用了哪些工具或 Skill：对可验证的答复给出有限评价，其余维度标未评分并指出需补什么证据。

评分完成后报告本次证据范围。需要源码级修复、发布或新的共享环境实测时，按用户授权另行开展。
