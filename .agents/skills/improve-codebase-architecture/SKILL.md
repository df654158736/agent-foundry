# 既有代码架构审查

当开发者要求做架构审查，或指定某段反复返工的链路时使用。先从用户要改善的任务和一条实际调用入手。已有术语表、ADR 或 Spec 可帮助识别已确认的决策。新项目的提交历史很短时，以实际调用者、重复修改和失败证据为准。

1. 用 [codebase-design](../codebase-design/SKILL.md) 的接口与职责判据检查痛点。沿一次改动追踪哪些调用者必须知道内部顺序、同一状态是否有多个写入者、错误能否从正常入口复现。有可靠历史时，用 git log 关注经常一起修改的文件，再检查其中的真实依赖。
2. 对疑似过薄的模块做删除测试：假如移除它，复杂度会消失，还是分散到调用者？对拟新增的抽象给出已存在的变化点、实际使用者，以及测试能从哪个接口覆盖它。
3. 只列证据支持的候选。每项说明文件与调用路径、用户或维护者承受的代价、建议改变的职责、应继续支持的合法路径、迁移风险及验证方法。多项候选按收益和回归风险排序；可以得出当前无需重构的结论。
4. 默认在当前会话提供结论。若用户需要展示复杂依赖，可附图。仅获审查授权时到结论为止；已获修复授权时，在证据充分的切片上实施并检查原问题、反例及相邻回归。可能改变产品契约的分歧交由负责人裁决。

例如恢复链路同时保留旧提案和新确认时，先查哪一方拥有已确认事实，然后检查能否在一次重试后保留该事实。仅凭目录层数或文件行数无法证明状态责任有误。
