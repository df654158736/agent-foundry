用 [目标对齐](../goal-aligned-design/SKILL.md) 核对责任、信息供给与交付。涉及模块边界时应用 [代码架构设计](../codebase-design/SKILL.md)。

从根入口读框架宪法与当前 SPEC。把用户原话写成一条能观察的任务：使用者、明确条件、希望得到的产物、合法替代路径、什么结果看起来成功却有错。权威资料可查就查；只请人裁决会改变结果且现有资料无法确定的政策。用一个真实切片贯穿到交付，再扩展场景。

**工具**放在 business/tools.py，注册到 TOOLS。给参数写类型、单位、时间范围和可取得的输入来源，docstring 说明何时使用。只有服务端能可靠取得的身份与权限在适配器内绑定。返回结构区分来源、状态、已查范围、空结果与错误；提示如何纠正一个无效参数并保留其余条件。读工具测正常、空、依赖失败与合法变体。写工具先核验真实副作用、确认和重试幂等，再开放给模型。

**提示词**在 business/system.md 写角色、用户目标、责任边界、可信依据、受阻交互。删除与工具 schema 重复的细节。工具签名和日期处理等确定性问题在所属层修。

**业务 Skill**在 business/skills/<name>/SKILL.md 写 name、description、适用条件、知识依据和更新责任。需要时把材料放在同目录并给相对路径。用另一种问法检查模型是否能自行发现并获取所需知识。不要将开发侧案例及期望注入正文。

运行 doctor 核对发现结果，使用 chat 测实际模型。把一次完整交付和独立依据连起来，再由 foundry-gold 扩展覆盖。框架升级时检查业务扩展是否绕过公开入口。

第一条真实场景先打通一项业务动作和一条独立核验路径。在 SPEC 记录实际作用域、数据版本、获准的模型目的地和能区分真成功与表面成功的判据。新增工具前明确用户需要的能力、可见输入以及什么证据能说明模型实际使用了它。模型合理省略可选动作时，单独记录未覆盖路径。

从空目录首次创作工具和运行时 Skill 时，使用[首个能力接入示例](references/first-capability.md)，其中包含工具注册、Skill 文件头、模型接线及首题验收步骤。
